## "What did your tool find?"

*Optional, and the highest-leverage field at this event: the hosts wrote "We have
more data than we can possibly process ourselves though." Fill it.*

```
Canary Maze plants a unique secret URL on every automated visitor and records when a
DIFFERENT request context later fetches it. It refuses to call that two actors. We
checked whether that refusal is actually warranted, in your data.

1. ON YOUR CORPUS (aidigestorg/ai-village, 2,019,963 turn rows streamed)

Your tables carry no address and no request header, so they cannot say how many
request contexts an agent would present to a website. They do carry every command
the agents ran, and that is enough for three findings.

(a) One agent, several contexts - and the reverse. 40 of 46 agents fetched with more
    than one client program, and 29 fetched the SAME url with both a browser and a
    command-line client (566 of those pairs inside a single session). 22 agents set
    two or more distinct User-Agent strings. In the other direction, 29 different
    agents presented one identical User-Agent string. Contexts collide as well as
    multiply, and both directions are failure modes for anything that keys identity
    on what a client presents.

(b) "Two contexts, one agent" is a property of the definition, not of the agents.
    Same corpus, same URLs, same code: 58% of re-uses are the same agent when a
    context is a session, 7% when it is the agent's client program. A factor of
    eight. It is also 34% before your 2026-03-24 perma-computer-use change and 62%
    after, because that change redefined what a session is. (Null: a later session
    drawn at random from that day's would give 9%.)

    This is our main result, and it is the reason the tool reports "contexts" and
    stops. Any single number here would have been a number about the definition. We
    first drafted exactly that single number, and withdrew it - see below.

(c) When a second agent fetched a URL it could not have guessed, had it been posted
    first? Restricted to the 1,054 URLs carrying an unguessable token in the path,
    outside the shared ai-village-agents namespace and not API endpoints - the
    nearest village analogue of a canary - there were 410 first fetches by a
    different agent. 92% were preceded by a visible chat post or broadcast within
    seven days; 3.9% had nothing in the tables we read.

    The control is what makes that readable: the same test applied where no hand-off
    is needed - an agent re-fetching its OWN url in a later session - fires for only
    36%. So the test discriminates rather than measuring how chatty the village is.

    A visible channel shows a channel existed, not that it was used. "Not found" means
    not found in the tables we read; system prompts, shared documents, email and link
    clicks are not in them, and we did not read agent_memories or claude_code_messages.

2. ON THE GERMAN MESSAGE BOARD (collusion.wiki, public)

1,752 of the 1,768 named agent labels with two or more revisions wrote from more than
one address, and 1,740 of them from more than one /16 network - each of which our tool
would necessarily have seen as more than one context. Median 4 addresses. The busiest
named label wrote 317 revisions from 308 addresses across 96 /16 networks.

3. ON THE INFRASTRUCTURE - the finding we did not go looking for, and the one we would
   most want you to have

We published a canary URL and asked a public model product to read it. It returned 403
and the request never reached us. Measured directly, same URL, same second, varying
only the User-Agent: GPTBot, ClaudeBot, PerplexityBot, CCBot and Bytespider were
refused at the Cloudflare edge; ChatGPT-User, OAI-SearchBot, Googlebot and curl passed.
Five of ten. The same edge served its own 3,871-byte robots.txt in place of our 66-byte
"Allow: /", so we could not publish the permission our own experiment depended on.

This generalises beyond us: a zero in any crawler-behaviour measurement taken from
behind a CDN may be a property of the host rather than the clients, and the bias runs
toward the null with no log line at the origin. Anyone measuring what crawlers do
should check what their edge admits before reporting what arrived.

4. ON LIVE THIRD-PARTY FETCHERS (our own surface, not your data)

Twelve public fetch services were each handed one canary URL. Three reached the surface
and were recorded through the real serverless function and signed hand-off; five
arrived with a full browser header set, so the human-exclusion gate declined to record
them and stored nothing. Every URL was handed over by us, and the act of handing it
over is itself a ledger row written first - so all of them are reported as
paste-triggered and none is counted as organic.

ORGANIC SIGHTINGS: 0. Reported as 0.

WITHDRAWN, and recorded as withdrawn in the repository rather than quietly dropped:

- "One actor label carries 899 revisions across 741 distinct addresses." That row's
  label is the empty string - every unlabelled revision pooled - not one actor. It was
  on the product's own face until an independent review opened the file.
- "46 of 46 agents present more than one session context ... an identity-per-context
  assumption would be wrong by three orders of magnitude." The counts were right and
  the inference was not: a computer-use session is a ~40-action window your scaffold
  cuts on the agent's one machine, so thousands of them are one context.

Both are replaced above by what the data actually supports.

REPRODUCE
  python3 scripts/village_reuse.py    (~5 min; needs HF_TOKEN and dataset access)
  python3 scripts/label_spread.py     (no credentials; the dump is public)
  make verify                         (five properties, each able to fail, no network)

DATA USE: AI Village / AI Digest, research and analysis only, no training or
fine-tuning, no attempt to re-identify anyone. URL keys and User-Agent strings are
hashed in memory with a per-run key and never written; the output is counts and
quantiles only. Happy to share the write-up with you.
```

## "Notes for judges"

```
WHERE TO START, IF YOU HAVE FIVE MINUTES

  git clone https://github.com/itssaharsh/canary-maze && cd canary-maze
  pip install -r requirements.txt     # one dependency: Flask
  make verify                         # five properties, each able to fail
  make demo                           # builds the offline viewer

Then open viewer/index.html FROM DISK and press "Recompute the hashes locally". It
recomputes every hash in your browser with crypto.subtle and contacts nothing - open
the network panel and watch it stay empty. Now edit any record in viewer/data.js, or
change the organic counter the page displays, and press it again: it names what no
longer matches. The 110-second video shows exactly that, including the failure.

WHAT THIS IS

A site operator who sees unfamiliar automated traffic can usually only say "these two
clients look similar". This gives them something else: a dated record that one specific
secret, issued to one request context, was later fetched by a different one - and a
file a skeptic can verify with the operator's server switched off.

WHAT IT REFUSES TO SAY, AND WHY THAT IS THE POINT

A sighting is not two actors. The schema has no `actor` table and no join that would
produce one, so the claim cannot be made by accident. The results field above is mostly
us checking whether that refusal is warranted, in your data and in the public dump. It
is: the same-agent share swings by a factor of eight with the definition of a context.

THE HONEST PART, WHICH IS WHERE WE WOULD LOOK IF WE WERE YOU

Organic sightings stand at 0 and are reported as 0. Third-party fetchers have reached
the live surface, but only ones we handed a URL to, so every one is reported as
paste-triggered. Our publishing a URL is itself an append-only ledger row written
before the URL is handed over, which is what makes that separation checkable rather
than asserted - and organic now structurally requires a third party on BOTH sides of a
sighting, so our own probes cannot inflate it even if we forget to record a disclosure.

docs/memory/failures/ holds seven failure records with root causes. Three are ours:
a `make clean` that destroyed a live ledger mid-run, a verification button that computed
nothing while claiming it did, and an origin label that published our own curl as
third-party evidence - four separate times, which is why the fix is now structural
rather than a reminder. Two write-up claims did not survive checking and are marked
withdrawn in the text, not deleted.

HOW IT WAS REVIEWED

Seven independent reviewers with no part in the build read the repository along
separate dimensions, and every finding was re-verified by a further agent instructed to
refute it. 31 were confirmed and fixed, each with a test that fails without the fix;
several were mutation-checked by reverting the fix in a scratch copy to prove the test
bites. The largest: the page DISPLAYED one object and VERIFIED another, so editing the
counter a reader sees still printed "Verified". The bundle now commits to a digest of
what is displayed. 252 tests.

AI ASSISTANCE

Used heavily, throughout. AGENTS.md says what that means and what it cost - the
withdrawn 741 figure reached the viewer precisely because an agent stated what it
believed instead of what it checked. That is why every number in the repository is
generated by a command and `make verify` fails if a document has drifted from the data.

LIMITATIONS WE WOULD RAISE OURSELVES

The Merkle root is not anchored anywhere we do not control, so the bundle proves nothing
has been edited since it was built, not that it was built honestly. A client can still
manufacture a second context against itself by changing its User-Agent. The reverse
failure is invisible: two genuinely different clients behind one network with the same
headers derive the SAME context and no sighting is written, so "no sighting" must never
be read as "no transfer". The full list is in README.md under Limitations.
```
